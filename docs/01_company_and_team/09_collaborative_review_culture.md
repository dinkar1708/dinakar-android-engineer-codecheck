# 🔍 Collaborative Code Review Culture & Communication Guidelines

**Reference Baseline:** Standards adapted from upstream repository review practices (see [Technical References](../references.md#7-github-api--assessment-standards))  
**Analyzed Artifacts:** 12 Closed Pull Requests, Code Reviews, Inline Comments, and Discussion Threads  

---

## 📌 1. Executive Summary: Communication Philosophy

High-performing engineering teams operate on **exceptional psychological safety, collaborative problem solving, explicit badge categorization, and respectful, polite communication (Keigo + Emojis in Japanese contexts)**.

Key cultural traits observed:
1. **Explicit Badge Categorization:** Reviewers and authors categorize comments with visual badges (`must`, `nits`, `memo`, `FYI`, `imo`).
2. **Review Level Settings:** Every PR uses a standardized review level checkbox to establish reviewer expectations up front.
3. **Softened Suggestions ("〜かも", "〜という印象"):** Reviewers avoid demanding language; they suggest improvements humbly and invite the author's input.
4. **Author Memos (`review-memo`):** Authors proactively leave inline self-review comments explaining non-obvious changes before reviewers even ask.
5. **Constructive & Appreciative:** Generous use of praise (`ステキなご対応`, `ありがとうございます！`, LGTM images, emojis `🙏`, `💪`, `✨`, `🙇`).

## 🏷️ 2. Review Badge Taxonomy & Conventions

Engineers use [Shields.io](https://shields.io) markdown badges at the top of inline comments to make intent crystal clear:

| Badge | Visual / Markdown | Usage & Meaning | Example Context |
| :--- | :--- | :--- | :--- |
| **MUST** | `![must-badge](https://img.shields.io/badge/review-must-red.svg)` | Critical requirement or blocker. Must be addressed before merge. | Dependency mismatch detected via `androidDependencies` task. |
| **NITS** | `![nits-badge](https://img.shields.io/badge/review-nits-orange.svg)` | Minor improvement, typo, or style preference. Non-blocking. | Newer patch release available (e.g. AGP `8.0.2` instead of `8.0.1`). |
| **MEMO** | `![memo-badge](https://img.shields.io/badge/review-memo-lightgrey)` | Author explanation / rationale. Added by the PR author to guide reviewers. | Explaining why `tasks.register` was used or why AGP Assistant added a property. |
| **[FYI]** | Plain text `[FYI]` | For Your Information. Helpful context, external links, documentation. | Community forum thread showing how to handle multiline outputs in Actions. |
| **[imo]** | Plain text `[imo]` | In My Opinion. Architecture/design suggestion open for discussion. | Proposing an environment variable for a shared configuration string. |

## 🗣️ 3. Japanese Phrasing & Vocabulary Bank

### Reviewer Phrases (Polite, Softened, Constructive)
- **Making Requests:**
  - `〜していただけると助かります 🙇` *(It would be helpful if you could fix...)*
  - `〜ご確認の上修正お願いします！` *(Please verify and update!)*
- **Softening Opinions:**
  - `〜かもですね 👀` *(Might be ...)*
  - `〜という印象を受けました 🤔` *(I got the impression that...)*
  - `〜を想定しても良いかもしれません` *(We might want to consider...)*
- **Acceptance / Backing down gracefully:**
  - `そこまで重要ではないので、今のままでマージしてしまってもいいかもです 🙇` *(It's not critical, so fine to merge as is!)*
  - `なるほど...! 良さそうな気がしています` *(I see! Looks good to me.)*
- **Praise & Approval:**
  - `様々なステキなご対応ありがとうございます ✨` *(Thank you for the variety of wonderful improvements!)*
  - `一箇所コメントしましたが、良い感じですね 👍` *(Left one comment, looking great!)*
  - `ありがとうございます！！ ![LGTM](https://lgtmoon.dev)`

### Author Phrases (Humble, Responsive, Action-Oriented)
- **Reporting Fixes:**
  - `<commit-hash> にて修正いたしました！` *(Fixed in commit <hash>!)*
  - `自分の手元でも確認できました。 <hash> にて修正いたしました！` *(Verified locally and fixed!)*
- **Agreeing with Reviewer:**
  - `仰るとおり、〜したほうが良さそうですね。` *(Indeed, doing ... seems better.)*
- **Requesting Re-review:**
  - `いただいたフィードバックを対応いたしました。お手数ですが、再度確認をお願いいたします 🙏` *(Addressed your feedback. Sorry for the trouble, please take another look!)*
- **Humility / Checking Understanding:**
  - `自分の認識違いだったら申し訳ないです 🙏` *(Apologies if I misunderstood!)*
  - `おや、最後まで入力済みでpushしたはずが… 失礼しました。` *(Oops, thought I pushed the full text... apologies!)*

## 💬 4. Case Studies: Constructive Feedback Patterns

### 🔹 Case Study 1: Android Gradle Plugin Upgrade
- **Background:** Upgrading AGP, Gradle wrapper, Navigation Safe Args, and documenting Android Studio version.
- **Q1 (Lead Reviewer):** `[must-badge]` Running `gradle androidDependencies` reveals mismatch in `lifecycle` and `coroutines` libraries.
  - **Reply (Author):** Confirmed locally. Bumped dependencies to matching patch versions.
- **Q2 (Peer Reviewer):** `gradle.properties` has new options generated by AGP Upgrade Assistant. Should we leave these for developers to configure?
  - **Reply (Author):** *"仰るとおり、候補者にお任せしたほうが良さそうですね。"* Reverted the auto-added properties.
- **Q3 (Peer Reviewer):** In README, should Gradle be written as 8.0.1?
  - **Reply (Author):** Clarified that Gradle is 8.0 while AGP is 8.0.1. Reviewer conceded: *"なるほど...! 良さそうな気がしています"*.
- **Q4 (Lead Reviewer):** `[nits-badge]` AGP `8.0.2` and Studio Flamingo Patch 2 just came out.
  - **Reply (Author):** Updated both immediately with commit references.
- **Author Memo:** Proactively added `[memo-badge]` on `tasks.register('clean', Delete)` explaining it fixes a Gradle warning.

### 🔹 Case Study 2: Token Permission Boundaries in CI
- **Background:** GitHub changed default `GITHUB_TOKEN` permissions to `none` on private repos, breaking workflow execution.
- **Inquiry (Author):** *"自分にはマージ権限がないので、マージ可能であれば、マージまでお願いれば有難いです。"* (I don't have merge permissions; please merge if good.)
- **Discussion:** Initial change gave `write`, but private repos also need `read`. Updated PR subsumed the changes with `read/write`.
- **Reply (Lead Reviewer):** Verified on a test private repository, apologized for slight delay, closed earlier attempt, and merged the updated PR.

### 🔹 Case Study 3: Network Authentication & Tooling Migration
- **Background:** Updating network dependencies and authentication header format.
- **Q1 (Lead Reviewer):** Tested on test repo, but the Action failed with an error. Could author investigate?
- **Reply (Author):** Diagnosed regex delimiter issue requiring `sed -E`. Provided run logs and verification link showing the fix.
- **Outcome:** Lead Reviewer praised: *"様々なステキなご対応ありがとうございます ✨"* and merged.

### 🔹 Case Study 4: Clarifying Documentation Updates
- **Background:** Adding rules for generative AI and LLM tool usage in project documentation.
- **Q1 (Peer Reviewer):** *"もしや途中で途切れちゃってますか？"* (Did the text get cut off?)
- **Reply (Author):** *"おや、最後まで入力済みでpushしたはずが… 失礼しました。こちらにて修正済みです 🙏"*
- **Outcome:** Approved collaboratively with LGTM badge.

### 🔹 Case Study 5: Respectful Inquiry Resolution
- **Background:** Contributor submitted PR updating copyright year in license headers.
- **Response (Lead Reviewer):** Very respectful educational explanation: Cited Japanese Cultural Affairs Bureau & WIPO treaty showing copyright exists automatically from creation (author life + 50 years) so immediate year bumps aren't legally necessary. Asked if contributor would agree to close it.
- **Reply (Author):** *"テキストまで提示していただき、ありがとうございます。一括修正予定であれば大丈夫です。"* (Thank you for providing the explanation. If updating in batch later, perfectly fine.) -> Gracefully closed.

### 🔹 Case Study 6: CI Workflow Configuration Scoping
- **Background:** Added GitHub Actions workflow to replicate issue templates.
- **Discussion (Lead Reviewer):** `[imo]` Suggested defining repository name as an environment variable (`env:`).
- **Technical Research (Author):** Tested workflow-level vs step-level env. Found workflow env works in steps, but fails in `if:` conditional checks at job level (referenced community documentation).
- **Resolution (Lead Reviewer):** Conceded gracefully: *"なんと、、😱 workflow単位でenv記述できる想定でした。。そこまで重要ではないので、今のままでマージしてしまってもいいかもです 🙇"*.

## 🎯 5. Actionable Standards for Pull Requests

To uphold the highest level of engineering excellence, collaboration, and code quality, we apply these exact practices across all our Pull Requests:

1. **Use the Review Level Checklist in every PR:**
   ```markdown
   ## レビューレベルの設定
   - [ ] まったく見ないでApproveする(基本的には非推奨。)
   - [ ] ぱっとみて違和感がないかチェックしてApproveする
   - [x] 仕様レベルまで理解して、仕様通りに動くかある程度検証、動作確認までしてApproveする
   - [ ] その他 (以下にコメント記載)
   ```
2. **Include Self-Review Memos (`review-memo`) on tricky code:**
   - Put `![memo-badge](https://img.shields.io/badge/review-memo-lightgrey)` on non-obvious changes (e.g. why `CompositionLocalProvider` was chosen for locale switching, why Ktor `HttpResponse.status.isSuccess()` is explicitly checked, or why exponential backoff with full jitter is used).
3. **Include Local Verification Commands & Evidence:**
   - In PR descriptions, always write: `見た目の変更はありませんが、念の為動作確認しました。 (./gradlew clean assembleDevDebug)` or include screenshots for Compose UI.
4. **Tone & Attitude:**
   - Polite, collaborative, humble, showing deep attention to Android Gradle Plugin, toolchain compatibility, and team communication norms.
